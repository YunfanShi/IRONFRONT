# 0.39.4 单人流程验收决定与下一阶段

## 基线与决定

2026-10-11 开始时，仓库与 macOS 独立程序均为 0.39.3，分支为 `codex/unity-port`。0.39.1 已记录 AI 自主完成攻防胜利、征服自然失败，以及编辑器内五种部署路径；0.39.2/0.39.3 继续修复坦克输入和高帧率起步。原 [逐项对照表](UNITY_PARITY_038.md) 把 S1 征服、S2 攻防、S8 部署与结算列为“局部”，原因是缺玩家实机验收。

玩家在本轮明确表示已试玩失败局，结算和复活可用，并要求把此前指出的 S1/S2/S8 单人流程部分先按验收成功计算。据此，对照表将三项更新为 **通过（单人流程）**。这是玩家给出的验收决定；本轮没有重新录制完整战局、逐个复活地点的点击过程或 Console 日志，不将这些细节写成新取得的实机证据。

| 项目 | 本轮处理 | 仍需分开处理的差异 |
| --- | --- | --- |
| S1 征服 | 单人战局闭环按玩家决定验收通过 | 默认 100 票短局、最后一级按击杀数平票裁决尚未对齐原版 |
| S2 攻防 | 玩家反馈失败局、结算和复活可用；单人流程验收通过 | 扩人数后须回归 A→E 推进、自然失败和结算 |
| S8 部署与结算 | 玩家反馈复活与结算可用；单人流程验收通过 | 各部署地点逐项鼠标点击的独立录像未留，扩人数时回归 |

此次通过不意味着 S3–S7 或 N1–N3 已通过，也不代表整款游戏已经还原。清单仍按功能差异逐项关闭。

## 下一阶段：先完成 S3 的 8v8

目前 `PrototypeRuntime.BuildBots` 固定生成蓝、红双方各 4 名 AI，蓝方另有本地玩家，实际是 5v4；网页端可选 8/16/32/64 人每方。下一次实现先让菜单的 **8v8** 对应真实数量：蓝方 1 名玩家加 7 名 AI，红方 8 名 AI。人数选择须传入实际生成逻辑，HUD 或调试统计显示真实双方人数，不允许只改菜单文字。

8v8 的验收同时覆盖 S6 的基本稳定性：从菜单进入征服与攻防，核对两队人数和小队分配；在完整战局中观察 AI 占点、战斗与复活，记录 FPS、内存和明显卡路/停滞；确认部署、票数、胜负和结算未因增员回退。性能阈值要在实现时结合目标机器与原版体验明确记录，不预先宣称 16v16、32v32、64v64 可用。

8v8 达标后依次扩至 16v16、32v32、64v64；若某档无法稳定运行，应如实限制或隐藏该档，再处理 S5 的缺失载具、S4 兵种和 S7 表现。联机 N1–N3 仍在单人范围的规模与玩法之后验收。

## 本轮改动与验证

本轮只更新验收清单、任务记录和版本标识，不修改战斗、AI 或联机逻辑。0.39.4 是按仓库规则递增的修订版本号，不表示还原百分比。

Unity 6000.5.10f1 刷新资源后，执行 `IRONFRONT → Build macOS Standalone` 成功，Console 为 0 警告、0 错误。`IRONFRONT.app/Contents/Info.plist` 的 `CFBundleShortVersionString` 为 0.39.4；启动独立程序后，大厅显示 0.39.4。由于本轮未改战斗逻辑，此构建只验证版本一致与启动，不替代下一阶段的 8v8 战局测试。
